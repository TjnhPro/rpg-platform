# Editor — project-specific agent guidance

**Canonical owner:** Project/content authoring tools, document lifecycle, config inspection, references, validation, visual/Rule preview and data export.

Read root agent guidance first.

- [v0.3.4 Object Ordering & Relationships](../harness/checkpoints/scene-contracts-v0.3.4.md) adds reorderSceneObjects, SceneObjectReference and SceneObjectAttachment. Membership optionally captures layerKey/attachment; omitted fields stay absent for compatibility. Explicit order must be a full permutation, never z sorting. Attachment is one nonhierarchical authored intent within the same Scene/project; missing targets retained, self/cross-Scene rejected, no target lookup, traversal, parent/transform propagation or cycle enforcement. Existing create/add preserve these fields.

- [v0.3.3 Scene Membership & Asset Binding](../harness/checkpoints/scene-contracts-v0.3.3.md) adds createSceneMembership/addSceneObject/listSceneObjects/getSceneObject and four readonly types. Membership captures a Scene plus ordered owned object definitions and optional Phase 2 AssetReference values. It enforces scene-local IDs and project-local bindings, never target/kind resolution. Add returns a new candidate; old snapshots survive. No second object/Asset registry, Render instance, placement, relationship or draw-order semantics. Existing Scene/Object shapes remain unchanged.

- [v0.3.2 Visual Object Identity & Definition](../harness/checkpoints/scene-contracts-v0.3.2.md) adds createSceneObjectDefinition and readonly input/result types. Caller objectId is exact and scene-local; standalone capture does not enforce uniqueness or join a Scene. Optional displayName/classification are opaque labels, defaulting to null. Frozen scalar-only snapshots need no Asset, placement, backend or gameplay entity. No extension state bag or gameplay type registry is introduced.

- [v0.3.1 Scene Identity & Definition](../harness/checkpoints/scene-contracts-v0.3.1.md) adds Editor-owned createSceneIdentity/createSceneDefinition and four readonly input/result types. Empty definitions contain identity only; no object list, metadata, title/path, persistence or Render instance. Keys follow the existing project-local exact-string convention but Scenes are not Assets. Construction returns detached frozen records; caller owns identity stability/uniqueness. Manual public-root consumer is optional, without tests or automatic runtime CI.

- [v0.2.10 integration/closure review](../harness/checkpoints/asset-contracts-v0.2.10.md) is the current Phase 2 inventory and AR01–AR16 status matrix; older checkpoint descriptions record their original revision. Editor owns 35 Phase 2 additions (43 total root symbols). No new production capability in this checkpoint. Manual metadata evidence does not imply loaded assets, visual verification or Developer phase acceptance.

- [v0.2.9 Minimal Working Asset Reference MVP](../harness/checkpoints/asset-contracts-v0.2.9.md) demonstrates registration, two independent reference holders, relocation, explicit rebinding, typed missing/kind diagnostics and Render metadata handoff in one optional public-root manual consumer. No new public API or production source change. Locators are illustrative; ASSET_CONTENT_NOT_LOADED and VISUAL_NOT_VERIFIED remain explicit. Do not turn holders into Scene/gameplay objects or the example into an automatic suite.

- [v0.2.8 Editor–Render Asset Consumption](../harness/checkpoints/asset-contracts-v0.2.8.md) adds describeResolvedVisualAsset over factory-resolved records. Only authored kind image with an image source maps to Render's neutral descriptor; unresolved/nonvisual/missing-image-source return unsupported. Explicit nullable media hint is supplied by the caller, never guessed from metadata or suffixes. Consumer calls Render prepareVisualResource through its root; described and metadata-prepared never mean loaded/displayed. Source IDs, arbitrary metadata, dependencies and Editor objects do not cross this boundary.

- [Phase 2 v0.2.0 AR01/AR02](../harness/checkpoints/asset-contracts-v0.2.0.md): Editor owns authored asset IDs, source metadata, future catalog/reference resolution and diagnostics. Asset ID is caller-provided and stable within project scope, never inferred from filename/path or a numeric external source ID. This is design-only: no asset API, catalog, resolver, importer or UI yet. Resolution must not perform IO or load Render resources; exported content must not require Client to import Editor.
- [v0.2.1 Stable Asset Identity](../harness/checkpoints/asset-contracts-v0.2.1.md) implements the public identity factory: exact nonempty whitespace-free projectId/assetId strings, case-sensitive pair equality, optional/null source text retained verbatim. Output is detached/frozen; label/path never supply implicit identity. No uniqueness/catalog or metadata descriptor. Developer's latest instruction defers review to the final step; do not block execution solely on earlier checkpoint review gates.
- [v0.2.2 Asset Classification & Metadata](../harness/checkpoints/asset-contracts-v0.2.2.md) adds `createAssetDefinition` and readonly metadata/definition types. Kinds classify resource/data, never game roles; kind strings remain open. Factory creates schemaVersion 1 records, reuses identity validation and deeply detaches/freezes portable JSON metadata, retaining unknown extension keys. No Render resource, UI state, parser, catalog, serializer or migration is added.
- [v0.2.3 Resource Locator & Composite Sources](../harness/checkpoints/asset-contracts-v0.2.3.md) adds project-relative locators and optional definition input sources (output defaults to a frozen empty list). Preserve source order; repeated roles support pages, exact duplicate role/locator pairs are rejected. Locators use literal slash-separated paths with no normalization, traversal, drive/URL syntax or backslashes. No IO, path-based identity or resource loading; lexical validation does not prove symlink containment or file existence.
- [v0.2.4 Asset Reference & Dependency Contracts](../harness/checkpoints/asset-contracts-v0.2.4.md) adds `createAssetReference` and input/snapshot types: explicit projectId+assetId, nullable expectedKind and opaque subresourceId, no target object pointer. Definition dependencies default to a frozen empty list; direct targets must be project-local and unique by asset key, preserving declaration order. Forward references are allowed without a catalog. Missing target keys are invalid structure; target existence/kind/subresource resolution is deferred to v0.2.6. No Scene/Entity module or graph traversal.
- [v0.2.5 Asset Catalog & Reference Resolution](../harness/checkpoints/asset-contracts-v0.2.5.md) implements a factory-created project-local immutable catalog: ordered definitions list, exact get, register/update/remove returning validated candidates. Duplicate IDs and foreign definitions are rejected. Minimal resolver now returns exact catalog definitions or explicit unresolved reasons (project, missing target, kind, unsupported subresource); this advances the earlier planned minimal lookup to this task, while full diagnostics remain v0.2.6. No IO, automatic dependency resolution, global registry/cache, UI or persistence.
- [v0.2.6 Missing Reference & Validation Diagnostics](../harness/checkpoints/asset-contracts-v0.2.6.md) adds diagnoseAssetReference/diagnoseAssetDefinition with typed frozen results, stable code, target hints, precise path and primitive details. Existing factories remain the validation authority and still throw TypeError; only their internal structured failures become invalid diagnostics. Unknown host exceptions propagate. First-error priority is documented; every result reports fileExistence NOT_CHECKED, never physical file missing. No subresource-missing assertion without producer data, auto-repair, scanner or UI.
- [v0.2.7 Asset Relocation, Rebinding & Compatibility](../harness/checkpoints/asset-contracts-v0.2.7.md) adds relocateAssetSource (one ordered locator, identity retained), rebindAssetReference (one explicit target validated by the resolver) and readAssetDefinitionSnapshot (complete current schemaVersion 1 records). Metadata extensions round-trip; unknown structural fields/versions reject without a result. Construction factories are not versioned snapshot readers. No physical move/replacement inference, host persistence, automatic holder rewrite or migration.

- Follow the [Editor–Render boundary](../harness/checkpoints/editor-render-v0.1.0.md). v0.1.0 imports are bootstrap compilation only, not an operational preview consumer.
- [v0.1.1](../harness/checkpoints/editor-render-v0.1.1.md) adds a package-root host adapter for session descriptors. It is not preview UI or renderer initialization; target creation/mounting/removal stays host-owned.
- [v0.1.2](../harness/checkpoints/editor-render-v0.1.2.md) adds explicit host-binding initialization through the Render root. Editor calls the lifecycle; it does not own its state machine. Bound is not graphics-ready.
- [v0.1.3](../harness/checkpoints/editor-render-v0.1.3.md): use public disposal before removing the host target, then drop caller-owned handles/snapshots. Render never destroys host-owned targets. No preview manager is implemented.
- [v0.1.4](../harness/checkpoints/editor-render-v0.1.4.md): consume/forward safe Render failure diagnostics through the public root. Unknown exceptions remain unknown; presentation policy is host-owned. No UI, fallback or retry behavior is implemented.
- Current [v0.1.5 ER04/ER10](../harness/checkpoints/editor-render-v0.1.5.md): the Editor preview-host adapter owns one session slot, disposes before replacement, and supports null as explicitly unavailable preview capability. Mounted means session initialized, not a rendered frame. No DOM host/UI is implemented.
- [v0.1.6 ER11–ER13](../harness/checkpoints/editor-render-v0.1.6.md) records compatibility and portability limits. Keep null/unavailable distinct from unsupported graphical targets and failures; future Render features require public API consumer analysis, never Editor/private backend imports or a silent mounted-to-GPU-ready reinterpretation.
- [v0.1.7 ER14](../harness/checkpoints/editor-render-v0.1.7.md) supplies a separate [manual browser entrypoint](manual/README.md). It awaits public Render graphics acquisition, submits one frame and disposes via the public lifecycle; it is not imported by the Editor root. Existing preview-host APIs stay binding-only. No Three import, loop, framework or automated browser verification is allowed in the demo.
- Use Render's package root, never `three`, `@types/three`, Render source paths or private backend classes. Editor owns host UI and session-reference orchestration; Render owns its resources and their cleanup. The separate v0.1.7 graphics path owns backend cleanup; existing preview-host adapters remain binding-only.
- [v0.1.8 ER15](../harness/checkpoints/editor-render-v0.1.8.md) records integration/closure evidence without a new API. The manual entrypoint is separate from the public preview-host adapter; do not imply mounting submits a frame. Keep manual visual review and phase acceptance open for Developer.

- Editor + Runtime Render => reusable scene/asset/object authoring. Do not assume visual NPC/Monster implies a shared RPG mechanics schema.
- Editor + Runtime Engine => configure what the **active game's Runtime** actually supports. Runtime is semantic owner; UI is the authoring surface.
- Preview gameplay uses the actual Runtime rule implementation. Do not write independent movement/damage/loot algorithms into Inspector or preview.
- Editor exports **data**, not a compiled game/client/server implementation.
- Keep project UI state, authored content and runtime sandbox state separate. Preserve unknown authored fields where possible; avoid destructive save operations.
- Learn from JXQY's Project/Document/Map/Skill/Goods/Playtest workflows, not its fixed skill/monster formats.
- MVP 1 can place a visual NPC without committing to HP, AI or Drop. No generated UI tests.
